Overview

trace-api is a FastAPI service that exposes POST /api/traces (and batch) with no auth so internal services and the Java EDC extension can POST events quickly. Events are stored in Postgres (hanover.trace_events). The trace-dashboard-ui Next.js app calls authenticated GET endpoints to list traces, show waterfalls, stats, and the EDC access matrix.

A single user action (e.g. QR lookup) shares one trace_id (UUID). Optional span_id / parent_span_id nest steps for timeline views.

1. How it works today (this repository)

After this section, tutorials explain why these steps exist; the last section reframes the same story in “pure connector” language.

2. Tutorial: Eclipse EDC (what the jargon means)

Eclipse Dataspace Components (EDC) are software connectors that sit between a participant’s internal systems and a federated dataspace. Instead of sharing one database password, each side exposes a connector. The connector enforces contracts (who may see which data, under which policy) before any payload moves.

Control plane vs data plane

PartRoleIn this demo
Control plane (CP)Policy, catalog, contract negotiation, transfer orchestration. Exposes a Management API for your apps and speaks DSP to remote connectors.repair-edc-cp, dpp-edc-cp
Data plane (DP)Moves bytes. Validates tokens from a transfer (EDR). For HttpData assets, forwards HTTP to a configured backend URL.repair-edc-dp, dpp-edc-dp

Typical sequence (names only)

  1. Catalog — Consumer learns what datasets exist (DSP to provider CP).
  2. Contract negotiation — Both connectors agree on an offer and policy (still CP / DSP).
  3. Contract agreement — Negotiation reaches a terminal success state.
  4. Transfer process — CPs start a transfer (e.g. HttpData-PULL).
  5. EDR (Endpoint Data Reference) — Consumer receives a short-lived token and a base URL (usually the provider data plane) allowed for this transfer.
  6. Data access — Some component performs HTTP to that URL with the token. In this repo, that component is repair-api, not a separate microservice.
Why repair-api talks to management and not only to DSP: The public Management API is the supported way for an application to drive catalog requests, negotiations, transfers, and EDR retrieval against its own connector. DSP is connector-to-connector; management is app-to-own-connector.

3. Tutorial: Gaia-X in this demonstrator

Gaia-X (here) is a trust and compliance layer on top of EDC: before or while a contract is evaluated, the provider can require evidence that the counterparty meets a policy (e.g. “Gaia-X compliant”).

What happens during negotiation

On dpp-edc-cp, a custom Java extension (gaiax-auth-extension) ties into the policy engine. When the policy requires gaiaxCompliant, the extension roughly:

  1. Resolves the other party’s identity via DID Web (see next section) and related metadata.
  2. Builds verifiable credentials and a verifiable presentation (VP).
  3. POSTs the VP to gx-compliance.
  4. If verification succeeds, negotiation can proceed; if not, it fails.

What Gaia-X is not here

There is no separate “Gaia-X bridge” in the default compose path for this repair flow. Compliance is triggered from inside the DPP control plane during policy evaluation. Trace events still let you see those steps in the dashboard.

4. Tutorial: DID Web & /.well-known

Connectors need a stable way to say “I am participant X.” This stack uses did:web: the DID document is served over HTTPS at a well-known path on the connector’s host.

Paths (via Caddy)

Caddy rewrites /.well-known/did.json (and related paths) to the control plane’s API context so the did-web-extension can serve:

  • /.well-known/did.json — W3C DID document (includes verification methods for the connector).
  • /.well-known/participant.json — Participant / self-description metadata used in the Gaia-X flow.
  • /.well-known/x509CertificateChain.pem — Certificate chain for TLS / signing alignment.

Hosts are per connector, e.g. edc-repair-shop.<domain> and edc-dpp.<domain> (see caddy/Caddyfile).

Both sides publish credentials

Provider (DPP) and consumer (Repair Shop) each run an EDC control plane with the same well-known endpoints on their own host. It is not only the passport publisher that needs a DID:

  • https://edc-dpp.<domain>/.well-known/did.json (and participant.json) — identity of the data provider connector.
  • https://edc-repair-shop.<domain>/.well-known/did.json (and participant.json) — identity of the repair shop / consumer connector.

When the repair shop asks for the ski product passport, the provider’s connector evaluates policy. For Gaia-X constraints it must resolve who the counterparty is — that means HTTPS fetches against the consumer’s well-known URLs (repair), not only the provider’s.

Why this matters: During Gaia-X verification the DPP connector must know who the repair connector is in a verifiable way. Fetching did.json / participant.json from edc-repair-shop.* is how that binding is established before gx-compliance sees a VP. In the Trace Dashboard → Access Control, open the Repair Shop (consumer) card to inspect the same documents the provider side resolves.

5. Mental model: connectors end-to-end (after reading the above)

This is the same story as section 1, described the way people often explain EDC aloud. The only deliberate difference is who performs the final HTTP pull: conceptually “the consumer side of the dataspace” pulls from “the provider side”; in code, that pull is implemented inside repair-api using the EDR your consumer CP helped create.

Repair Shop Web
  ↓ HTTPS
Repair Shop API  →  management  →  Repair EDC connector (control plane drives DSP)
  ↓ DSP (contract talk)
DPP EDC connector control plane  ←→  trust: provider + consumer did.json / participant.json (repair well-known) + Gaia-X VP to gx-compliance
  ↓ agreement + transfer
Data planes: consumer DP + provider DP participate in HttpData-PULL setup; provider DP serves bytes and calls dpp-api
  ↑ passport JSON
Repair Shop API  →  Repair Shop Web
  • Aligns with your description: Web → API → connector (CP negotiates with DPP CP) → verification (well-known + Gaia-X) → data plane path → DPP API → data back.
  • Implementation detail: The GET that hits dpp-edc-dp runs in the repair-api process; routing traffic through repair-edc-dp as an HTTP forward-proxy for that GET is not what repair_api/main.py does today.

Trace Dashboard (UI)

App: frontend/apps/trace-dashboard (APP_NAME=trace-dashboard). Features typically include: event log with filters, per-trace_id waterfall, aggregate stats, and the access matrix view backed by /api/access-matrix.

Login uses the same JWT pattern as other apps; set NEXT_PUBLIC_API_URL so the browser posts to /api on the traces host (Caddy splits UI vs API by path).
